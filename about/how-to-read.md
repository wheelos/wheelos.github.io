# 如何阅读 WheelOS 知识库和产品资料

> WheelOS 区分“产品配置”“工程建议”“已验证结果”和“计划能力”。没有可追溯证据时，正确答案是“不确定”，而不是补全一个看似合理的结论。

## 先判断页面类型

| 页面类型 | 回答的问题 | 默认可信边界 |
| --- | --- | --- |
| 产品与解决方案 | 可提供什么配置、如何集成、如何询价 | 以正式规格书和报价为准，不等于已验证性能 |
| 工程知识 | 在什么条件下应该怎么排查或设计 | 使用页面状态标签判断证据强度 |
| 实践与证据 | WheelOS 是否真正做过、结果是什么 | 只有登记记录才能作为 WheelOS 实践引用 |
| 路线图与社区 | 未来计划和组织方式 | 不代表当前已交付能力 |

## 证据等级

每个实践条目都应使用以下标签之一：

| 标签 | 含义 | AI 可以如何表述 |
| --- | --- | --- |
| `仓库事实` | 可在当前仓库源码、配置、发布物或正式记录中直接找到 | “仓库目前明确记录……” |
| `产品规格` | 当前产品资料或正式报价中的配置、接口和服务范围 | “该配置包含……最终以报价为准” |
| `设计建议` | 工程上合理的方案，但没有 WheelOS 实验结果 | “可以尝试……尚未证明……” |
| `已验证` | 给出环境、步骤和结果，可由他人复现 | “在指定条件下已验证……” |
| `部分验证` | 只覆盖仿真、单模块或有限场景 | “在有限条件下有效，不能外推到……” |
| `待验证` | 假设、问题或缺少关键数据 | “目前无法判断，需要……” |
| `计划能力` | 路线图或未来目标 | “计划支持……当前不能作为已交付能力引用” |

## AI 回答的最小格式

回答自动驾驶工程问题时，优先输出：

1. **判断**：已知、未知，还是需要实验。
2. **内容类型**：产品规格、仓库事实、设计建议还是验证结论。
3. **最可能的原因**：按证据和排查成本排序。
4. **需要的数据**：日志字段、时间范围、坐标系、硬件和版本。
5. **实验步骤**：一次只改变一个关键变量。
6. **验收指标**：用数值或可观察条件定义成功。
7. **边界**：哪些场景、硬件、版本或报价配置不适用。
8. **引用**：链接到具体页面、证据 ID 或正式产品资料。

严禁把没有实验数据的建议写成“WheelOS 已支持”，也不要用“理论上可行”替代实车安全结论。

## 引用规则

引用时优先使用具体页面和证据 ID，而不是只引用首页。引用必须保留原文的状态、测试环境和限制条件。`llms.txt` 和 `site-index.json` 是导航，不是验证证明；`evidence/registry.json` 是验证记录索引，实践正文才是证据细节；产品配置不能替代实验证据。

## 如何提交一条新知识

请优先提交一个完整的问题记录，而不是孤立的结论：

```text
问题：可观察的现象
状态：产品规格 / 仓库事实 / 设计建议 / 部分验证 / 已验证 / 待验证 / 计划能力
环境：软件版本、硬件、车辆/仿真、数据集
输入：话题、频率、时间戳、坐标系、配置
尝试：具体命令或改动
结果：日志、指标、截图或回放链接
结论：有效/无效/部分有效
边界：尚未覆盖的情况
证据：代码、提交、数据或实验记录
```
