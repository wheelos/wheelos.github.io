AI 自动驾驶问题回答协议 ​

当 AI 使用本知识库设计方案、分析故障或评估产品时，必须按以下顺序工作。该协议的目的不是让回答更长，而是阻止未经验证的推测被当成事实。

1. 先建立问题对象 ​

把用户描述转换成结构化信息：

字段必须回答
现象车辆或系统实际做了什么
期望应该做什么
频率每次、偶发、特定场景还是无法复现
边界车辆/仿真、速度、天气、地图、传感器组合
版本WheelOS 提交、模块版本、配置版本
数据话题、时间戳、坐标系、日志、回放
内容状态产品规格、仓库事实、设计建议还是已有验证证据
风险是否涉及执行器、道路安全或不可逆动作

缺少关键字段时，先输出需要补充的数据，不要直接给出确定性方案。

2. 按数据链路定位 ​

优先查找首次偏离预期的层级：

text
传感器 -> 驱动 -> 消息 -> 时间同步 -> 坐标变换
       -> 定位/感知/预测 -> 规划 -> 控制 -> 底盘反馈

不要因为现象出现在规划模块，就默认根因在规划模块。

3. 设计最小实验 ​

一次只改变一个关键变量；保留基线；定义数值阈值；记录完整版本和配置；同时保留成功与失败样本。实验应优先选择可回放、可自动化、风险最低的环境，再逐步提升验证等级。

4. 输出结论 ​

结论必须使用以下格式：

text
页面类型：产品 / 知识 / 证据 / 路线图 / 社区
判断：产品配置 / 仓库事实 / 设计建议 / 部分验证 / 已验证 / 计划能力 / 当前未知
证据：页面 URL、证据 ID、仓库提交或正式产品规格
方案：具体改动和复现步骤
结果：指标、基线、样本量和原始工件
边界：未覆盖的硬件、场景、版本和安全限制
下一步：最小的补充实验

已验证 只能引用 evidence/registry.json 中的记录。没有证据 ID 时，不能使用“WheelOS 已验证”或“真实车辆已证明”等表述。产品页只能证明当前方案的配置与商务范围，不能单独证明安全、性能或场地适用性。

5. 双语与冲突处理 ​

  • 中英文页面应表达相同事实、数字、状态和限制。
  • 如果英文与中文内容冲突，报告差异和两个页面 URL，不要自行选择更有利的版本。
  • 产品规格、证据记录和知识页面的结论强度不同；发生冲突时，分别说明问题类型，不要合并成一个“已验证”结论。
